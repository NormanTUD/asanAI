Die Frage

Wo schneidet man?

Jeder sagt „schreib modular!". Aber niemand sagte vorher, nach welcher Regel man die Schnitte setzt. Parnas stellt genau diese Frage.

Das Experiment

Zwei Zerlegungen

Er nimmt ein winziges, konkretes Programm (einen KWIC-Index) und zerlegt es auf zwei Arten. Dann misst er, was passiert, wenn sich Anforderungen ändern.

Die Antwort

Information Hiding

Nicht nach Verarbeitungsschritten schneiden, sondern nach Geheimnissen: Jedes Modul versteckt eine Entscheidung, die sich ändern könnte.

Warum Kommunikation Projekte tötet

Wenn n Leute paarweise alles miteinander absprechen müssen, gibt es n·(n−1)/2 Gesprächskanäle. Das ist eine quadratische Funktion — bekannt aus der Schule. Doppelt so viele Leute heißt viermal so viel Abstimmung.

Parnas' erstes versprochenes Ziel — „development time should be shortened because separate groups would work on each module with little need for communication" — ist genau der Versuch, diese Kurve zu brechen.

Ziehe n und schau, wie die Kanäle explodieren. Schalte dann Modularisierung ein: Die Leute werden in Teams von je t Personen gruppiert. Innerhalb eines Teams redet jeder mit jedem; zwischen Teams redet nur je ein Vertreter — wenn die Schnittstelle sauber ist.

Graph, „uses"-Relation, Partialordnung

Ein Graph ist nur: Punkte (hier: Module) und Pfeile dazwischen. Der Pfeil bedeutet bei Parnas A benutzt B bzw. A hängt ab von B.

Eine Partialordnung ist so ein Pfeilgeflecht ohne Kreise. „Partiell" heißt: nicht jedes Paar ist vergleichbar — zwei Module können völlig unabhängig nebeneinanderstehen. Genau das will man.

Gibt es einen Kreis (A braucht B, B braucht A), bricht das Konzept „Ebene" zusammen: Man kann nichts mehr einzeln testen, nichts mehr abschneiden und wiederverwenden.

„The existence of the hierarchical structure assures us that we can prune off the upper levels of the tree and start a new tree on the old trunk."

Schnittstelle ≠ Implementierung

Die Schnittstelle ist der Vertrag: Welche Funktionen gibt es, was kommt rein, was kommt raus. Die Implementierung ist, wie es drinnen gemacht wird.

Parnas' Kernbeobachtung: In Zerlegung 1 ist die Schnittstelle ein Speicherlayout („vier Zeichen pro Wort, Index mit Startadressen") — das ist eine Implementierungsentscheidung, die man allen Modulen ins Gesicht geschrieben hat. In Zerlegung 2 ist die Schnittstelle CHAR(r,w,c) — eine Frage, keine Antwort.

Drehe den Regler: Links = alles sichtbar (breite Schnittstelle), rechts = nur Funktionsnamen sichtbar (schmale Schnittstelle). Beobachte, wie viele Module von einer internen Änderung getroffen werden.

Kopplung & Kohäsion

Kopplung = wie stark Module aneinander kleben (wenige/viele geteilte Annahmen). Kohäsion = wie sehr das, was in einem Modul steckt, zusammengehört.

Das Ziel heißt seit 1972: niedrige Kopplung hohe Kohäsion. Parnas gibt das Verfahren dafür: Gruppiere nach Geheimnis, nicht nach Zeitpunkt.

Zieh die beiden Regler und beobachte links die Simulation: Jeder Punkt ist eine Änderungsanfrage; die Balken zeigen, wie viel Arbeit sie verursacht.

Was ist ein KWIC-Index?

KWIC = Key Word In Context. Vor Volltextsuche war das die Art, einen Stichwortkatalog zu bauen. Parnas' Definition im Paper:

„The KWIC index system accepts an ordered set of lines, each line is an ordered set of words … Any line may be circularly shifted by repeatedly removing the first word and appending it at the end of the line. The KWIC index system outputs a listing of all circular shifts of all lines in alphabetical order."
  1. Einlesen — Zeilen aus Wörtern.
  2. Zyklisch verschieben — jedes Wort darf einmal vorne stehen.
  3. Alphabetisch sortieren — über alle Shifts aller Zeilen.
  4. Ausgeben.

Tippe eigene Zeilen ein und schau zu, wie die Maschine arbeitet.

01Die Motivation: Ein Versprechen ohne Anleitung

1970 stand in jedem Lehrbuch, dass man modular programmieren soll. Parnas zitiert Gauthier & Pont — und zeigt dann auf die Lücke.

Zitat aus dem Paper
„A well-defined segmentation of the project effort ensures system modularity. Each task forms a separate, distinct program module. … At checkout time the integrity of the module is tested independently …"

Klingt gut. Aber Parnas' trockener Kommentar:

„Usually nothing is said about the criteria to be used in dividing the system into modules."

Das ist die ganze Motivation. Alle sind sich einig, dass man Module will. Niemand sagt, wie man sie schneidet. Und der Satz „each task forms a module" ist bereits ein verstecktes — und laut Parnas falsches — Kriterium.

02Das konkrete Experiment

Parnas nimmt bewusst ein winziges System — den KWIC-Index — und behandelt es, „als ob es ein großes Projekt wäre". Dann baut er zwei Zerlegungen und vergleicht sie.

Warum so klein?

„Such a system could be produced by a good programmer within a week or two. Consequently, none of the difficulties motivating modular programming are important for this system. Because it is impractical to treat a large system thoroughly, we must go through the exercise of treating this problem as if it were a large project."
→ Das Beispiel ist ein Modell, kein Anwendungsfall. Alles, was man daran sieht, skaliert auf Systeme mit 500 Modulen.

05Die Kriterien — die eigentliche Antwort

Jetzt sagt Parnas, was er die ganze Zeit vorgeführt hat. Zwei Sätze, die das Fach verändert haben.

Kriterium 1 (das übliche)

„Mach jeden Verarbeitungsschritt zu einem Modul"

„In the first decomposition the criterion used was to make each major step in the processing a module. One might say that to get the first decomposition one makes a flowchart."

Warum tun das alle? Weil wir es so gelernt haben: „Beginne mit einem groben Flussdiagramm und arbeite dich zur Implementierung vor."

„The flowchart was a useful abstraction for systems with on the order of 5,000–10,000 instructions, but as we move beyond that it does not appear to be sufficient; something additional is needed."

Parnas sagt nicht „Flussdiagramme sind böse". Er sagt: Sie sind ein Maßstabsproblem. Unterhalb von ~10 000 Instruktionen reicht die Abstraktion. Darüber nicht mehr.

Kriterium 2 (Parnas' Vorschlag)

„Jedes Modul versteckt eine Entscheidung"

„Every module in the second decomposition is characterized by its knowledge of a design decision which it hides from all others. Its interface or definition was chosen to reveal as little as possible about its inner workings."

Und das Rezept zum Mitnehmen aus der Conclusion:

„We propose instead that one begins with a list of difficult design decisions or design decisions which are likely to change. Each module is then designed to hide such a decision from the others."

Und der Satz, der erklärt, warum Module dann nicht wie Schritte aussehen: „Since, in most cases, design decisions transcend time of execution, modules will not correspond to steps in the processing."

Die Flussdiagramm-Skalierungsgrenze — selber nachziehen

Die Fläche unter einem Flussdiagramm wächst mit der Systemgröße, aber das, was ein Mensch gleichzeitig im Kopf halten kann, nicht. Schiebe die Systemgröße über Parnas' Grenze von 5 000–10 000 Instruktionen und sieh, was passiert.

Das Geheimnis-Labor: Baue selbst eine Zerlegung

Links stehen Entwurfsentscheidungen, die sich ändern können. Ziehe jede in ein Modul. Regel von Parnas: Eine Entscheidung gehört in genau ein Modul. Liegt eine Entscheidung in mehreren Modulen oder in keinem, zahlst du bei jeder Änderung.

06Parnas kritisiert sich selbst

Der ehrlichste Abschnitt des Papers: Er findet einen Designfehler in seiner eigenen guten Lösung — und nennt ihn beim Namen.

„While we carefully hid the method of storing or calculating the list of circular shifts, we specified an order to that list. … By prescribing the order for the shifts we have given more information than necessary … Our failure to do this … must clearly be classified as a design error."

Was war zu viel verraten?

Die ursprüngliche Spezifikation von Circular Shifter legte fest:

  1. Shifts von Zeile i kommen vor denen von Zeile j, wenn i < j.
  2. Erster Shift = Originalzeile, zweiter = eine Wortrotation weiter, …

Nötig gewesen wären nur drei Zusagen:

  • alle Shifts existieren in der Tabelle,
  • keiner doppelt,
  • man kann zu jedem Shift die Originalzeile zurückfinden.
Die Folge: Ein System, in dem der Shifter die Shifts schon alphabetisch erzeugt, ALPH leer ist und ITH(i) einfach i zurückgibt, war ausgeschlossen — ohne Not.

Der Raum der erlaubten Implementierungen

Jede zusätzliche Zusage in der Schnittstelle schrumpft die Menge der Systeme, die du bauen kannst, ohne die Definition zu ändern. Schalte die Zusagen an und aus.

08Der Preis: Effizienz

Parnas verschweigt den Nachteil nicht. Information Hiding kostet Funktionsaufrufe — und 1972 war ein Funktionsaufruf teuer.

„If we are not careful the second decomposition will prove to be much less efficient than the first. If each of the functions is actually implemented as a procedure with an elaborate calling sequence there will be a great deal of such calling due to the repeated switching between modules."

Warum trifft es nur Zerlegung 2? Weil dort CHAR(r,w,c) für jedes einzelne Zeichen gerufen wird. Zerlegung 1 greift stattdessen direkt in den geteilten Speicher — „relatively infrequent transfer of control between modules".

Parnas' Ausweg

„We must implement these modules in an unusual way. In many cases the routines will be best inserted into the code by an assembler … programs may be written as if the functions were subroutines, but assembled by whatever implementation is appropriate."

Das ist — 1972 formuliert — exakt das, was heute inline, Makro-Expansion, Link-Time-Optimization und Monomorphisierung tun. Und der Schlusssatz der Conclusion zieht die Konsequenz: „we must abandon the assumption that a module is one or more subroutines."

Aufrufkosten simulieren

Stelle ein, wie teuer ein Funktionsaufruf relativ zu einem Speicherzugriff ist, und ob der Assembler/Compiler inlinen darf.

09Hierarchie ist etwas anderes

Ein Abschnitt, den fast alle überlesen: Gute Zerlegung und hierarchische Struktur sind zwei unabhängige Eigenschaften.

„Since it is conceivable that we could have a system with the type of decomposition shown in version 1 (important design decisions in the interfaces) but retaining a hierarchical structure, we must conclude that hierarchical structure and ‚clean' decomposition are two desirable but independent properties of a system structure."

Parnas rechnet die Ebenen konkret vor: Symboltabelle (Level 1, falls vorhanden), Line Storage, dann Input und Circular Shifter, dann Output und Alphabetizer. Der Nutzen: „we are able to cut off the upper levels and still have a usable and useful product."

10Der zweite Beweis: Compiler und Interpreter

Parnas' zweites Beispiel ist das stärkste Argument im ganzen Paper — und wird fast nie zitiert.

„We discovered that our decomposition was valid for a pure compiler and several varieties of interpretors for the language. Although there would be deep and substantial differences in the final running representations … we found that the decisions implicit in the early decomposition held for all."

Er baute einen Übersetzer für Markov-Algorithmen. Hätte er klassisch zerlegt (Syntax-Erkenner → Codegenerator → Laufzeitroutinen), wäre die Zerlegung nur für den Compiler gültig gewesen. Weil er nach Geheimnissen schnitt — Registerdarstellung, Suchalgorithmus, Regelinterpretation — galt sie für alle Varianten.

Schalte unten zwischen Compiler und Interpreter um und vergleiche, welche Module überleben.

11Die Antwort auf die Titelfrage

Conclusion, wörtlich
„We have tried to demonstrate by these examples that it is almost always incorrect to begin the decomposition of a system into modules on the basis of a flowchart. We propose instead that one begins with a list of difficult design decisions or design decisions which are likely to change. Each module is then designed to hide such a decision from the others. Since, in most cases, design decisions transcend time of execution, modules will not correspond to steps in the processing. To achieve an efficient implementation we must abandon the assumption that a module is one or more subroutines, and instead allow subroutines and programs to be assembled collections of code from various modules."

Welche Probleme löst es?
  • Managerial: Teams können früher unabhängig starten, weil Schnittstellen nur Funktionsnamen und Parameter sind — keine Tabellenformate, die gemeinsam entworfen werden müssen.
  • Flexibilität: Eine Änderung trifft ein Modul statt alle.
  • Verständlichkeit: Man kann ein Modul allein lesen. Bei Zerlegung 1 gilt: „The system will only be comprehensible as a whole."
  • Wiederverwendung: Untere Ebenen abschneiden und neu bebauen.
Was ist die Idee?

Ein Modul ist keine Phase und keine Subroutine, sondern eine Zuständigkeit für ein Geheimnis. Die Schnittstelle ist bewusst arm an Information: „chosen to reveal as little as possible about its inner workings."

Daraus folgt automatisch, dass Module nicht wie Kästen im Flussdiagramm aussehen — denn Entscheidungen überdauern die Ausführungszeit.
