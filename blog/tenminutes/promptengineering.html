Prompting is communication.

You are not programming the model; you are creating a linguistic environment. Every role, example, and constraint narrows the space of plausible answers.

01 Set the environment

Role, specificity, structure.

A role primes the model with a style and a body of knowledge. Specific instructions reduce ambiguity. Delimiters separate instructions from data. Examples show the format you want better than a description often can. This is why a few-shot prompt (Brown et al., 2020) — a handful of input-output examples before the real request — often beats a longer description of the same rule.

The three message roles are not cosmetic either. The system message sets the standing instructions, the user message carries the request, and the assistant message holds the model's earlier turns. The model is trained to treat them differently, which is why a system instruction usually outranks a user instruction — and why prompt injection tries to smuggle a new system instruction into user data.

Negations are weak: telling a model not to think of a white bear can make the bear more likely. To suppress a concept, the model still has to represent it. Say what you want, not only what you do not want.

02 Keep it lean and testable

Iterate, do not decorate.

Long prompts are not automatically better. Every irrelevant sentence adds noise and costs tokens. Canonicalise the input, remove boilerplate, and make the task easy to verify.

Prompting is empirical. Change one thing, test it, and keep what works. Self-Refine turns that loop inward: the model critiques and revises its own output (Madaan et al., 2023). A prompt that is clear to a human is usually a good starting point for a model.

03 Prompting is not security

Untrusted text is an attack surface.

Prompt injection happens when text the model is supposed to read contains instructions. A web page, a document, or an email can tell the model to ignore its system prompt. Delimiters and clear roles help, but they are not a security boundary.

The defence is architectural. Give the model the least privilege it needs, separate instructions from data, validate tool calls, and keep a human in the loop for dangerous actions. A prompt that says 'never do X' is not a guarantee.

Prompting is still useful. Clear roles, specific constraints, examples, and canonical input reduce ambiguity. But clarity is not the same as security, and a model is not a trusted interpreter of untrusted text.

Background

The Master Principle

All prompt engineering techniques reduce to one idea: control the probability distribution. Every technique -- roles, delimiters, CoT, few-shot, structured output -- is a tool for collapsing the model's output space from “anything” to “exactly what I need.”

The best prompt engineers do not memorize techniques; they understand which degrees of freedom the model has, and systematically lock them down until only the correct output path remains. The most familiar example is chain-of-thought (Wei et al., 2022): asking for intermediate steps keeps the model from committing to an answer in a single token and gives it a place to check its work. It is a prompt-level version of the scratchpad idea, and it is the subject of Day 27. Extensions such as Tree of Thoughts explore several branches before committing (Yao et al., 2023).

Background

Specify Output Format

Define a strict schema (JSON, CSV, YAML) that constrains the model's generation pathway. This reduces format errors, not factual ones: a syntactically perfect object can still contain a wrong value. If the runtime supports constrained decoding, the schema can be enforced token by token; otherwise the model can drift, and the output needs validation.

Background

Use Delimiters

Triple quotes, XML tags, and dashed lines create hard boundaries between instructions and data. This reduces prompt leakage where the model confuses your system prompt with the user content.

More background

The Art of Talking to a Stochastic Parrot

Prompt engineering is the practical craft of communicating with Large Language Models, not by hacking their weights, but by hacking their input. Since an LLM is fundamentally a next-token predictor wrapped in a chatbot interface, the way you phrase, structure, and constrain your input is the single most powerful lever you have.

Think of it like this: you are not programming the model. You are creating a linguistic environment that statistically steers it toward your desired outcome. Every word you choose reduces the entropy of what comes next.

More background

Define the Role

Assigning a persona acts as a semantic filter that primes the model to activate specific regions of its training distribution. A “senior Rust engineer” persona pulls different weights than a “Shakespearean poet,” even on the exact same question.

Practical notes

When a good prompt still fails.

A prompt can be clear and still fail because the model lacks the knowledge, the task is ambiguous, or the context is too long. Prompting cannot fix a missing capability. A prompt is also model-specific: the same wording can work on one model and fail on another because their instruction-following training differs. Treat a prompt as part of the system, version it, and re-test it after a model upgrade.

Prompt injection, contradictory instructions, and untrusted text are security and design problems. Use permissions, validation, and human review for anything that matters.
