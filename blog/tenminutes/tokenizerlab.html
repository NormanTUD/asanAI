Chopping text into tokens.

A model never sees words. It sees tokens — chunks of text — and turns each one into a vector. That single decision explains why models struggle to count letters, why some languages cost more, and why a vocabulary entry is not the same thing as a learned concept.

01 The first cut

Computers need numbers. Text is not numbers.

The very first thing a language model does is chop the input into small pieces called tokens. We can first think of these as words, but they do not have to be. A token can be a whole word, a sub-word, a number, a punctuation mark, or a single byte. Humans think in words; the model thinks in tokens.

Most tokens are common words or word fragments. understanding can split into under + stand + ing. That is the quiet genius of the design: a word the model has never seen can still be assembled from pieces it knows by heart. The vocabulary never has to grow, and transformer is just trans + form + er.

The aha

It can read words it has never seen.

Break every unfamiliar word into familiar pieces and nothing is truly new. The trade-off is that the model never sees the word as a single object — it sees a sequence of pieces.

03 The consequence

Tokenization is a bias, not a preprocessing detail.

How is the vocabulary built? The workhorse is Byte Pair Encoding (BPE): start from characters, repeatedly merge the most frequent adjacent pair in the training text, and stop at the target vocabulary size. Unigram / SentencePiece fits a unigram language model over candidate subwords and prunes the set that best explains the corpus. Byte-level BPE starts from all 256 bytes, so every input is representable; the price is that a non-ASCII character can take several tokens.

A tokenizer is fixed before a single weight is trained, and it prices every language differently. A word that is one high-frequency subword in the dominant language may need several tokens in another. For many lower-resource and non-Latin scripts, the result is routinely several times more tokens per word than English. The same meaning is longer at the token layer.

That compounds in three places at once: cost (tokens are billed per token), context (a longer tokenization fills the window sooner), and capacity (fewer words fit in the same attention budget). A language is partly priced by a vocabulary trained on a corpus that was, in practice, not that language.

The stranger failure is qualitative. Sometimes a string becomes a single token during tokenizer training, but the model almost never sees that token during pretraining. It exists in the vocabulary, has an ID and an embedding row, but its parameters are barely trained. The result is a glitch token: an input the tokenizer handles perfectly and the model has no learned meaning for.

The canonical examples come from the GPT-2/GPT-3 tokenizer: SolidGoldMagikarp, petertodd, externalToEVA. The likely cause is a mismatch between the corpus used to train the tokenizer and the corpus used to train the model. A token can be frequent in one and absent from the other, leaving its embedding close to random initialization. The lesson is not “avoid one weird string”; it is that a vocabulary entry is not a learned concept.

The aha

A token is a slot, not a meaning.

The tokenizer decides which slots exist; the training data decides which slots get filled. When the two disagree, the model can talk fluently about a string it has never learned.

04 The bestiary

What else the cut breaks.

Once you look at text as tokens rather than characters, several ordinary failures become visible. None is exotic; all follow from cutting at statistically convenient boundaries.

Numbers1234 and 1235 may split differently. Arithmetic then runs across pieces that do not line up with digits.
SpacesA prompt ending in “is” and one ending in “is ” can have different next-token distributions. Whitespace is content.
UnicodeThe same visible “é” can be one code point or two. Emoji, flags, and combining marks multiply the cases.
PortabilityToken IDs are not portable. A different model family has a different vocabulary; its token counts are not a budget for another.

Byte-level BPE removes the worst failure: if the alphabet is all 256 bytes, every possible input has a tokenization and nothing is ever unknown. But it does not remove the inflation — a Thai sentence is still more bytes, hence more tokens, than the same sentence in English. Byte-level is the floor, not the fix. The frontier is to shrink or remove the discrete bottleneck altogether: byte-to-byte models and continuous “pre-token” spaces. Whether that closes the gap or merely moves the bias is an open question.

The engineering checklist is short: measure tokens per word for every language you serve; audit the vocabulary against the model’s data; test spelling, numbers, whitespace, emoji, combining marks, rare names, and mixed scripts; treat the tokenizer as a versioned contract.
