Give the model a library card.

An LLM can only use what it memorized or what is in its context. RAG adds a search step: find the relevant passages, put them in the prompt, and answer from them.

01 The pipeline

Index, retrieve, generate.

RAG starts with a corpus. Documents are split into chunks: small, overlapping passages that can be retrieved independently. An embedding model turns each chunk into a vector. The same model turns the question into a vector in the same space — if the chunk model and the query model differ, the similarity scores are meaningless.

A similarity score, usually cosine similarity, rates every chunk against the query. The score is not a probability; it is a measure of alignment in the embedding space. The system selects the top-k chunks (or everything above a score threshold) and formats those passages into the prompt. The language model then answers from that context.

The key division of labour: the embedding model and the index do the searching; the LLM only reads the selected passages. That is why the embedding model, the chunking strategy, and the ranking rule matter as much as the generator itself.

02 Why RAG still fails

Retrieval is not truth.

Retrieval can miss the right passage, return a misleading one, or find text that is outdated. The model can ignore the retrieved context or blend it with its own memorized errors. Chunking and ranking are design decisions, not details.

RAG is not a truth machine. It is a way to make the model's answer depend on documents you can inspect. Citations and evaluation are what make that useful.

03 The parts the happy path hides

Chunking, hybrid search, reranking.

Chunking is a design decision. Too small and the passage lacks context; too large and the retriever has to match a lot of irrelevant text. Overlap helps avoid cutting a fact in half. Contextual retrieval adds a short summary of the surrounding document to each chunk.

Hybrid search combines keyword matching with dense vectors. Keyword search is good at names and exact terms; dense retrieval is good at paraphrase. A reranker can then score the top candidates with a more expensive model before the answer is generated.

The failure modes are real: the right passage may be missing, the wrong passage may be ranked first, or the model may ignore the context. Evaluation and citations are what make RAG useful rather than decorative.

RAG and fine-tuning solve different problems. RAG changes what the model can see; fine-tuning changes what the model is like. Use RAG for facts that change, private documents, and anything that needs a citation. Use fine-tuning for a format, a tone, a tool-calling convention, or a behaviour the base model will not pick up from a prompt. The two can be combined: a fine-tuned model that reads retrieved passages is a common production pattern.

Background

Making RAG work

RAG mitigates the “lost in the middle” problem by shrinking the context to a handful of chunks, but it does not abolish it: a relevant chunk placed in the middle of even a short retrieved set can be underused, so ordering matters. Put the strongest evidence first or last, and keep the set small enough that the model can actually weigh it.

When RAG fails, the first diagnostic question is where. If the answer is not in the retrieved chunks, it is a retrieval failure: fix the chunking, the embedding model, the index, or the query. If the answer is in the chunks and the model still gets it wrong, it is a generation failure: fix the prompt, the ordering, or the model. Treating every bad answer as a model problem wastes time on the wrong half of the pipeline.

Background

Retrieval, in Depth

The happy path — embed the corpus, retrieve the nearest chunks, hand them to the model — is what the sections above walk (see also Semantic search). This deeper half is what happens in practice, and it is mostly about the parts the happy path hides — how you cut the corpus into chunks (the single highest-leverage, least-discussed knob), how you combine keyword and semantic search, how you rerank with a second, more expensive model, and — the half the demos never show — why retrieval-augmented generation so often underperforms and how to find out whether your failure is in the retrieval or the generation.

Background

RAG and Long Context Windows

In-context learning (ICL) relies on whatever the user manually puts in the prompt. RAG automates the selection using vector search. The LLM itself does not know the difference; it just sees tokens in its context window either way. The magic of RAG is in the retrieval step before the LLM runs. That also means RAG cannot create knowledge that is absent from the corpus: it can only put the right page in front of the model.

More background

The RAG Pipeline, Step by Step

Step 1, Chunk the documents. Split each source (PDF, webpage, database row) into small, overlapping passages, typically 200–500 tokens. Overlap ensures no information falls between the cracks.

Step 2, Embed and index. Run each chunk through the embedding model and store the vector together with the text and its metadata (source, date, section). A vector database is the system that holds those vectors and can return the nearest ones quickly; it is a search index, not a second model.

Step 3, Embed the query. Use the same embedding model, or the vectors live in different spaces and the comparison is meaningless.

Step 4, Retrieve. Score the query against the index, usually with cosine similarity, and take the top-k chunks or everything above a threshold. Hybrid search adds keyword matching for names and exact terms.

Step 5, Rerank (optional). A cross-encoder or a stronger model re-scores the shortlist by reading the query and the passage together. It is slower than vector search and usually more accurate.

Step 6, Generate. Insert the selected passages into the prompt, instruct the model to answer from them, and ask for citations. The model is now doing reading comprehension, not recall.

More background

RAG vs. In-Context Learning (ICL)

In-Context Learning is when you put examples or instructions directly in the prompt and the LLM “learns” the task on the fly, with no weight updates, just pattern-matching over the provided tokens. ICL and RAG are complementary: ICL shows the model the task, RAG supplies the facts. A good prompt often uses both — a few worked examples plus the relevant passages.
